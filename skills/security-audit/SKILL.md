# 安全审计与合规规范

## 一、代码安全审计 (SAST)

### RULE-SEC-CODE-001: SQL 注入防护
```
✅ 强制: 检查所有 DAO/Mapper 层代码
✅ 强制: 禁止拼接 SQL (`$`)，必须使用预编译 (`#`)
✅ 工具: Checkstyle / SonarQube / FindBugs
```

### RULE-SEC-CODE-002: 硬编码密钥检查
```
✅ 强制: 代码库中严禁出现明文密码、AK/SK、Token
❌ 禁止: `String password = "123456";`
✅ 推荐: 使用 GitHooks (如 `trufflehog`) 扫描提交
```

### RULE-SEC-CODE-003: 第三方依赖安全 (SCA)
```
✅ 强制: 定期扫描 `pom.xml` / `build.gradle`
✅ 强制: 修复 CVE 评分 >= 7.0 (High/Critical) 的漏洞
✅ 工具: OWASP Dependency Check / Snyk
```

## 二、运行时安全审计 (DAST)

### RULE-SEC-RUN-001: 身份认证与鉴权
```
✅ 强制: 所有非公开接口必须校验 Token
✅ 强制: 敏感操作 (如删除、修改权限) 必须二次验证或校验权限
❌ 禁止: 越权访问 (IDOR - Insecure Direct Object References)
```

### RULE-SEC-RUN-002: 数据传输安全
```
✅ 强制: 全站 HTTPS (TLS 1.2+)
✅ 强制: 敏感字段 (手机号、身份证) 在传输层必须加密
❌ 禁止: 明文传输用户凭证
```

### RULE-SEC-RUN-003: 输入验证与输出编码
```
✅ 强制: 严格校验所有输入参数 (XSS 防护)
✅ 强制: 对输出到页面的内容进行 HTML 编码 (防止存储型 XSS)
```

## 三、基础设施安全审计

### RULE-SEC-INFRA-001: 容器安全
```
✅ 强制: 镜像扫描 (Trivy / Clair) 无高危漏洞
✅ 强制: 容器以非 root 用户运行
✅ 强制: 限制容器 Capabilities (Drop ALL, add minimal)
```

### RULE-SEC-INFRA-002: 网络安全
```
✅ 强制: 数据库、Redis 禁止公网访问
✅ 强制: 最小化开放端口 (仅开放 80/443)
✅ 强制: 配置 WAF 防护 SQL 注入和 CC 攻击
```

## 四、安全审计检查清单 (Pre-Release Checklist)

发布上线前，必须逐项确认：

### 1. 代码层面
- [ ] 是否已修复所有 SonarQube Critical/Blocker 问题？
- [ ] 依赖库是否存在已知高危漏洞？
- [ ] 是否清除了所有临时调试代码和注释？

### 2. 配置层面
- [ ] 生产环境配置文件是否加密？
- [ ] 数据库连接池密码是否已替换为生产凭据？
- [ ] 是否关闭了 Swagger (生产环境)？

### 3. 数据层面
- [ ] 是否已备份数据库？
- [ ] 数据迁移脚本是否经过验证？
- [ ] 敏感数据是否已脱敏？

## 五、AI 辅助安全自检规则

### 当用户请求代码审查时:
1. ✅ 自动扫描 SQL 拼接风险
2. ✅ 自动扫描硬编码密钥
3. ✅ 自动检查 XSS/CSRF 防护措施

### 当用户请求生成配置时:
1. ✅ 自动提示将敏感信息移入环境变量或 Secret
2. ✅ 自动建议关闭不必要的端点 (如 Actuator shutdown)

## 六、违规处理规则

| 违规级别 | 处理方式 |
| :--- | :--- |
| **P0 (致命)** | **立即阻断发布**，必须修复 |
| **P1 (严重)** | **警告并记录**，限期修复 |

### P0 违规示例:
```
❌ 场景: 代码中发现了 AWS AK/SK 明文
✅ AI 动作: 立即警告，并建议使用环境变量或 IAM Role 替代。
```

### P1 违规示例:
```
⚠️ 场景: 使用了包含中危漏洞的 logging 库
✅ AI 动作: 提示升级版本，但不阻断开发环境部署。
```
