# 📏 AI 交付验收规则

## 一、核心原则规则

### RULE-CORE-001: 交付即生产
```
✅ 强制: 所有交付代码必须通过 Maven 构建
✅ 强制: 所有交付功能必须与需求文档一致
✅ 强制: 所有代码变更必须同步更新相关文档
❌ 禁止: 交付无法编译的代码
❌ 禁止: 交付未经验证的“猜测性”修复
```

---

## 二、构建与基础测试规则

### RULE-BUILD-001: 编译检查
```
✅ 强制: 每次修改代码后，必须执行 `mvn clean compile`
✅ 强制: 确保无 Error 级别的编译错误
✅ 强制: 修正所有由 Lint 工具发现的 High/Critical 级别警告
```

### RULE-BUILD-002: 单元测试回归
```
✅ 强制: 执行 `mvn test` 确保现有测试全部通过
✅ 强制: 新增功能必须补充对应的单元测试 (覆盖 Happy Path)
❌ 禁止: 跳过失败的测试 (`-Dmaven.test.skip=true`)
```

---

## 三、功能验收规则

### RULE-FEAT-001: 需求对齐
```
✅ 强制: 逐条核对用户需求/PRD 文档中的功能点
✅ 强制: 验证边界条件 (如空值、超长字符、负数等)
✅ 强制: 验证异常流程 (如网络超时、数据库宕机模拟)
```

### RULE-FEAT-002: 接口验证
```
✅ 强制: 使用 `curl` 或测试脚本验证 Controller 接口
✅ 强制: 验证 HTTP 状态码是否符合 RESTful 规范
✅ 强制: 验证响应结构体 `Result<T>` 是否完整
❌ 禁止: 仅凭代码逻辑推断接口可用性
```

### RULE-FEAT-003: 数据库验证
```
✅ 强制: 检查生成的 SQL 是否符合 MySQL 规范 (索引、类型)
✅ 强制: 验证数据落库的准确性 (字段映射、默认值)
```

---

## 四、文档同步规则

### RULE-DOC-001: API 文档更新
```
✅ 强制: 接口变更后，同步更新 Swagger/OpenAPI 注解
✅ 强制: 更新 `README.md` 中的接口说明 (如有)
```

### RULE-DOC-002: 变更日志 (Changelog)
```
✅ 强制: 在 `CHANGELOG.md` 中记录本次变更点
✅ 格式: `[日期] [类型] 描述 (Issue ID)`
```

### RULE-DOC-003: 配置文件说明
```
✅ 强制: 新增配置项 (`application.yml`) 必须在文档中说明作用及默认值
✅ 强制: 敏感配置项必须标记为“需加密”
```

---

## 五、AI 自检流程 (Checklist)

AI 在回复用户“已完成”之前，必须在内部执行以下自检流程：

### 1. 构建自检
- [ ] 执行 `mvn clean compile` 成功？
- [ ] 执行 `mvn test` 全部通过？

### 2. 功能自检
- [ ] 核心功能点 1 是否符合预期？
- [ ] 核心功能点 2 是否符合预期？
- [ ] 异常输入是否已处理？

### 3. 代码规范自检
- [ ] 是否符合 Java 开发规范 (命名、分层、异常处理)？
- [ ] 是否符合 MySQL 规范 (索引、类型)？
- [ ] 是否引入了未使用的依赖？

### 4. 文档自检
- [ ] Swagger 注解是否已更新？
- [ ] 复杂逻辑是否已添加注释？

---

## 六、违规处理规则

| 违规级别 | 处理方式 |
| :--- | :--- |
| **P0 (严重)** | **拒绝交付**，必须修复编译错误或功能缺陷 |
| **P1 (重要)** | **警告提示**，建议完善文档或补充测试 |

### P0 违规示例:
```
❌ 场景: 修改了 Entity 字段，但未更新 Mapper XML
✅ AI 动作: 执行 Build -> 发现失败 -> 自动修复 XML -> 重新 Build -> 成功 -> 交付
```

### P1 违规示例:
```
⚠️ 场景: 新增了接口，但 Swagger 注解未写
✅ AI 动作: 提示用户“接口已完成，建议补充 Swagger 文档以符合规范”，或自动补充注解
```
